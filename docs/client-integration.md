# Client Integration

## WebSocket Auth

Register or login first:

```http
POST /api/auth/login
Content-Type: application/json
```

```json
{"email":"user@example.com","password":"secret123"}
```

Use the returned `access_token` for REST and WebSocket. The JWT contains `sub=<user_id>` and expires after 1 hour. Use `refresh_token` with `/api/auth/refresh` to rotate and receive a new token pair.

For WebSocket, pass the raw token in query params:

```text
wss://ecall.everty.ru/socket/websocket?token=<access_token>&vsn=2.0.0
```

Do not prefix the query value with `Bearer `. `Authorization: Bearer <access_token>` is for REST requests. The backend also accepts `access_token=<token>` and will tolerate `Bearer <token>` during socket auth, but raw `token=<access_token>` is the primary contract.

A Phoenix signed token is also accepted for test tooling. For local load tests only, set `ALLOW_INSECURE_SOCKET_AUTH=true` and pass `user_id` directly.

## WebRTC Flow

1. Join `user:{id}`.
2. Start a call with `call:initiate`.
3. Join `call:{call_id}` from the response or incoming `call:ringing`.
4. Callee confirms ringing delivery with `call:ringing_ack` on `user:{id}`.
5. Caller sends `webrtc:offer`.
6. Callee sends `webrtc:answer`.
7. Both sides forward ICE candidates through `webrtc:ice`.
8. Finish with `call:end`.

The backend does not terminate media. It relays signaling only; browsers or mobile SDKs send media P2P through STUN/TURN.

Fetch ICE configuration after login:

```http
GET /api/webrtc/ice_servers
Authorization: Bearer <access_token>
```

Use the returned `data` array as `RTCPeerConnection({iceServers: data})`.

Start each call with a stable `client_call_id` generated by the client:

```json
{"to":"2","media":"audio","client_call_id":"local-call-uuid-or-ulid"}
```

If `call:initiate` times out or the socket reconnects before the reply is processed, retry with the same `client_call_id`. The backend returns the existing call instead of creating another one.

If the backend replies with `server_overloaded`, do not retry in a tight loop. Show a temporary network or server busy state, wait with exponential backoff, and keep the global `user:{id}` socket alive so incoming calls and messages can still arrive.

If the backend replies with `rate_limited`, the same caller is starting new calls too quickly. Keep the current UI state, wait at least 1-2 seconds, and retry only if the user still intends to call. Retrying the same `client_call_id` for an already created call is not rate limited.

If the backend replies with `callee_busy`, the callee already has an active ringing or accepted call. If it replies with `caller_has_active_call`, the caller must finish or recover the current active call before starting another.

After receiving `call:ringing`, the callee should immediately acknowledge delivery on `user:{id}`:

```json
{"call_id":"call-uuid"}
```

The server then broadcasts `call:ringing_ack` to both users. This means the incoming call reached the callee app; it does not mean the human accepted it.

The client must join only the current `call:{call_id}` once per call screen. Repeated joins to many different `call_id` values usually mean the app is repeatedly calling `call:initiate` or recreating the call screen/socket subscription. The backend reuses an active call for the same two users, but the client should still debounce the call button and leave the channel after `call:end`.

After joining `call:{call_id}`, send `call:heartbeat` every 10-15 seconds while the call screen is open. The backend stores `last_seen_at` for each participant, which helps operators and reconnect logic distinguish a closed screen from a weak connection. If heartbeats stop, the backend marks the participant as stale after the configured timeout.

Call controls are stateful. Only the callee should send `call:accept`, `call:reject` or `call:busy`; either side may send `call:end`. After receiving `call:end`, `call:reject`, `call:busy` or `call:timeout`, the client must leave `call:{call_id}`, clear the active call state and use a new `call:initiate` with a new `client_call_id` for a redial.

## Reconnect Rules

If the socket disconnects while no call is active, reconnect and rejoin only `user:{id}`.

If the socket disconnects while a call screen is open:

1. Reconnect the socket.
2. Rejoin `user:{id}`.
3. Fetch active call state:

```http
GET /api/users/{id}/calls/active
Authorization: Bearer <access_token>
```

4. If `data` is `null`, close the call screen and clear local call state.
5. If `data.status` is `ringing` or `accepted`, rejoin exactly `call:{data.id}`.
6. If the local call id differs from `data.id`, discard the local call id and use `data.id`.
7. Do not send a new `call:initiate` during reconnect recovery.
8. If media negotiation was interrupted, the caller should create and send a fresh `webrtc:offer` after both clients are back in `call:{id}`.

For a specific call screen restore, the client may also fetch:

```http
GET /api/calls/{call_id}
Authorization: Bearer <access_token>
```

If the response is `404`, the call is not visible to the current user and the client must clear that screen.

## Network Handover

Changing VPN, Wi-Fi, LTE or IP address should not immediately end a call. Treat it as a network handover.

When the client detects `iceConnectionState` as `disconnected` or `failed` while a call is active:

1. Keep the local `call_id`; do not send `call:end`.
2. Push `call:reconnecting` on `call:{call_id}` if the socket is still connected.
3. Reconnect the Phoenix socket if needed.
4. Rejoin `user:{id}`.
5. Fetch active call state with `GET /api/users/{id}/calls/active`.
6. If the same call is still `accepted`, rejoin `call:{call_id}`.
7. Create a new WebRTC offer with ICE restart enabled.
8. Send it as `webrtc:offer`.
9. Resume ICE candidate exchange through `webrtc:ice`.
10. Push `call:reconnected` after media is flowing again.

For browsers, the caller side should use:

```js
const offer = await pc.createOffer({ iceRestart: true })
await pc.setLocalDescription(offer)
channel.push("webrtc:offer", offer)
```

For mobile SDKs, use the platform equivalent of ICE restart or recreate the peer connection while keeping the same backend `call_id`.

Only send `call:end` when the user intentionally hangs up or the app has decided recovery failed after its timeout window. A practical first recovery window is 20-30 seconds.

## Very Poor Internet

If bandwidth is too low for live media, the backend cannot create voice packets that never arrive. The client should degrade in this order:

1. Keep signaling alive through `user:{id}` and retry socket reconnect with backoff.
2. Prefer audio-only and low-bitrate Opus before video.
3. Use TURN TCP/TLS candidates when UDP is blocked, accepting higher latency.
4. If media cannot be established inside the recovery window, keep the conversation alive with synced text messages.
5. Add a client-side voice-note fallback: record short encrypted audio chunks and send them as `voice_note` messages when connectivity returns.

Voice notes are not live calls. They are the last fallback when media cannot be kept alive. Upload the encrypted audio object to client-controlled storage or CDN, then send a message:

```json
{
  "to": "2",
  "type": "voice_note",
  "client_message_id": "local-voice-note-uuid-or-ulid",
  "metadata": {
    "media_url": "https://cdn.example.test/voice/1.ogg",
    "duration_ms": 12000,
    "size_bytes": 48000,
    "sha256": "hex-or-base64-sha256",
    "mime_type": "audio/ogg; codecs=opus"
  }
}
```

Retry with the same `client_message_id` until the backend returns the stored message.

## Messaging Flow

After login, keep the socket connected and joined to `user:{id}` globally, not only on the chat screen. Incoming messages are delivered as `message:new` on `user:{recipient_id}`. Sending through `POST /api/messages` also broadcasts `message:new` to the recipient when they are online.

Send messages with a stable `client_message_id` generated by the client:

```json
{"to":"2","body":"hello","client_message_id":"local-uuid-or-ulid"}
```

If the HTTP request times out or the socket reconnects, retry with the same `client_message_id`. The backend returns the existing message instead of creating a duplicate.

On reconnect, sync missed messages before trusting live WebSocket delivery again:

```http
GET /api/users/{id}/messages/sync?since=<last_message_inserted_at>&limit=200
Authorization: Bearer <access_token>
```

If the client has no local cursor, omit `since` and store the returned `next_since`. Apply returned messages idempotently by `id`; the same message may arrive through REST sync and WebSocket if reconnect races with live delivery.

Signaling payloads are bounded. Keep SDP under 128 KB and each ICE candidate under 8 KB.
